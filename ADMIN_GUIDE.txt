STATE ISSUE 3.3.0 — ADMINISTRATOR GUIDE
========================================

Inmate profiles have three staff-set review levels:
- Routine (green): no additional review flag is currently set.
- Needs review (orange): check the profile, request history, and recorded reason.
- High risk (red): heightened staff review; the recorded reason is required.

These are visual staff cues, not automated decisions or an independently verified
risk assessment. Routine does not mean the inmate has never had a problem. Choose
based on documented facts; the level never auto-approves or denies a request.
The same color and text appear on linked requests. Profile review-level changes
are retained in profile history.

Open a request's "Request activity & history" disclosure to see request snapshots,
decisions and reasons, item issues and voids, timestamps, staff labels, and request
comments in chronological order. Older requests may not have a full activity
history if details were not retained at the time; older item labels may reflect
the current catalog name if the item was not snapshotted before a rename.

Purpose
-------
This guide is for the person who installs, operates, updates, and recovers the
State Issue host. Keep a copy with the application and make sure more than one
trusted staff member knows where it is.

Repository and reference
------------------------
Source code, published updates, and project history:
https://github.com/XLFatFluffy/State-Issue-App

Use the repository's Issues page for reproducible software problems. Do not
post names, inmate records, database files, screenshots, exports, passwords,
or network credentials to a public issue. Include the app version, Windows
version, steps to reproduce, and sanitized error text instead.

1. IMPORTANT SECURITY AND PRIVACY LIMITS
----------------------------------------
- The app has no login, authentication, or role-based access. Every person
  who can reach it has the same access to view and change records.
- Display names are optional and can be changed by the user. They are labels,
  not verified identities or a security audit trail.
- Run the server only on a trusted private network/VPN. Never forward its port
  from a router or expose it directly to the public internet.
- Treat the database, its backups, offline browser data, and CSV/JSON exports
  as sensitive operational records. Restrict access and store copies securely.
- Use standard Windows accounts for routine work. Limit administrator rights
  to people responsible for maintaining the host.

2. NETWORK AND INTERNET REQUIREMENTS
------------------------------------
The host computer runs the server on TCP port 8787. Workstations connect using
the host address configured in OPEN_STATE_ISSUE.bat. All computers must be able
to communicate through the same approved local network or VPN.

Normal app use on an already configured local network does not require internet.
Internet access is needed for optional online Python installation, downloading
pywin32 during the first service installation, and downloading updates with
UPDATE_STATE_ISSUE.bat. If internet is unavailable, do not repeatedly run an
online installer or updater; the installed app can continue on its local
network. Schedule updates for when the host can reach GitHub.

For the host computer use START_STATE_ISSUE.bat, which opens
http://127.0.0.1:8787/. Do not use the workstation shortcut on the host for
offline operation. For workstations use OPEN_STATE_ISSUE.bat or the exact URL
configured inside that file. Opening Stateissue.html directly from a folder
does not connect to shared data.

If the host's local network/VPN address changes, update OPEN_STATE_ISSUE.bat on
each workstation and the matching host/local-address restrictions in
SETUP_NEW_COMPUTER.bat. Re-run the setup script as administrator and test from
a workstation. Keep firewall access limited to the approved private network;
never disable the firewall as a troubleshooting shortcut.

3. INITIAL HOST SETUP
---------------------
1. Copy the complete project folder to a permanent location on the Windows
   host, such as C:\StateIssue. Do not run it from Downloads, a temporary
   folder, or removable media.
2. Run SETUP_NEW_COMPUTER.bat. It checks for Python, checks required files,
   runs test_server.py, and offers Python installation if needed. Allow the
   firewall rule only on the intended private network/VPN.
3. Run INSTALL_STATE_ISSUE_SERVICE.bat as administrator. The initial install
   downloads pywin32, registers the "State Issue Server" Windows service, and
   configures automatic startup and restart attempts.
4. Run START_STATE_ISSUE.bat on the host and confirm the app loads at
   http://127.0.0.1:8787/.
5. From each workstation, connect to the approved host network/VPN and run
   OPEN_STATE_ISSUE.bat. Confirm that shared changes appear on both computers.
6. Confirm the database and backups folder are in the expected location. Make
   and verify a backup before entering operational data.

The Windows service runs in the background and starts with Windows. Keep the
host powered on and prevent it from sleeping while staff need the app. Closing
the browser does not stop the service. To check or control it, open Services
(services.msc) and find "State Issue Server".

4. DAILY OPERATION AND CONNECTIVITY
-----------------------------------
- Host: open the app with START_STATE_ISSUE.bat.
- Workstations: connect to the host network/VPN, then use OPEN_STATE_ISSUE.bat.
- Confirm the app's save/connection status before relying on a change.
- Review Dashboard / Today's Changes and Setup / Recent Changes as appropriate.
- Use the separate CONNECT_AND_TROUBLESHOOT.txt for step-by-step diagnostics.

Host-only offline work: the host's localhost tab can continue using browser-
stored data when the server is unreachable. The app indicates that changes are
saved on this computer and will sync. Keep that browser profile and its site
data intact until sync finishes. After connectivity returns, verify that the
pending status clears and the records appear on the shared app.

Workstation outage: a workstation may display the last data it loaded, but
cannot save changes until it reconnects. Do not assume a visible form or record
was saved. Stop entering changes until the app confirms saving.

Reconnect conflict: if changes were made on the host while it was offline and
the server received newer changes elsewhere, the app may show RECONNECT
CONFLICT. The server copy remains active and the host's offline copy is kept
in that browser. In Setup, export/save that offline copy, compare it with the
server's current records, re-enter only the needed changes, and discard the
offline copy only after review.

Routine staff workflows
------------------------
- Keep inmate profiles and recorded sizes current. Check identity and source
  information before creating or changing an operational record.
- Review each request and decide its item lines. Record reasons when needed.
  Issue only approved quantities through the app's issue workflow; use partial
  fulfillment when only part of a request can be supplied.
- Set each item/size's reorder trigger and desired stock target under Setup >
  Stock Targets & Reorder Alerts. The dashboard flags quantities at or below
  the trigger; inventory guidance shows recent demand and quantity needed to
  reach the target. These settings do not place orders or change stock.
- Record stock receipts and adjustments through inventory transactions. Run
  the Monthly Inventory Check and reconcile differences before saving.
- Use messages, replies, and comments for factual operational context. Link a
  message to its request or inmate when useful; it will appear on that record.
  Mark messages complete when the work is done, or reopen them if more follow-up
  is needed. Deleting a message permanently removes its replies too. These
  records are shared; do not use them for information that must remain private.
- Use Setup > Report a Problem or Suggestion to describe app flaws and requested
  changes. Include the area, exact button or field, steps to reproduce, and a
  request ID, name, or MDOC number when it helps identify the record. Review
  incoming reports in Setup and update their status as you review them. Reports
  are shared with everyone who can access the app and are included in backups.
  A host connection is required to send a report; it will not wait offline.
- Use Reports for review and export only the data needed. CSV and JSON files
  are downloaded to the browser's download location and may contain sensitive
  records. Store them securely and remove unneeded copies according to policy.
- Use Setup > Back Up to Host to create an on-demand SQLite snapshot in the
  host's backups folder. Daily and monthly backups are created automatically
  by the server. Download JSON Export only when you deliberately need a
  portable copy; it downloads to the current browser's workstation.
- Before a restore, the app automatically creates a fresh host-side SQLite
  safety copy. If that backup fails, restore is cancelled and current data is
  left unchanged. Restore still replaces all current records if it proceeds.

5. DATA FILES AND BACKUPS
-------------------------
By default the live SQLite database is state_issue_v2.db beside the program;
backups are in the backups subfolder. If STATE_ISSUE_DATA is configured, the
database and backups are in that data folder instead. Confirm the actual
location before maintenance.

The running server creates:
- Daily backups named backups\daily_YYYY-MM-DD.db; keeps the latest 30.
- Monthly backups named backups\monthly_YYYY-MM.db; keeps the latest 12.
- Backups at server startup and periodic checks while it is running.
- On-demand backups named backups\manual_YYYY-MM-DD_HHMMSS_microseconds.db
  when staff select Back Up to Host, and immediately before a restore; keeps
  the latest 30.

Automatic and on-demand host backups are on the same computer as the database.
At least daily, copy a recent backup to a separate approved, secure device or
location. Keep the copy protected from unauthorized access, loss, and
ransomware. Do not store production data or backups in the source repository.

Verify a backup
---------------
Run VERIFY_BACKUP.bat and provide a .db backup path, or drag a backup onto the
batch file. A PASSED result verifies that the database can be read; it does
not replace testing a full recovery procedure. Verify the newest daily backup
at least monthly and before restoring it. The check is read-only.

Restore a backup
----------------
Restoration replaces the current live database and loses changes made after
the chosen backup. Schedule downtime and tell users to stop work first.
1. Choose a backup and run VERIFY_BACKUP.bat on it. Continue only if it passes.
2. Stop "State Issue Server" in Services (services.msc).
3. Make a separate safe copy of the current state_issue_v2.db. Do not delete it.
4. Copy the verified backup into the configured data folder and name the copy
   exactly state_issue_v2.db. Keep the original backup untouched.
5. Start the service. Open the app on the host and confirm the expected
   records and dashboard are present. Then test from a workstation.
6. Keep the replaced database and backup until the restored app is confirmed.

If the database is unreadable or the restore is uncertain, stop and preserve all
copies. Do not repeatedly attempt recovery on the only copy; get help from an
experienced administrator.

6. UPDATING AND MAINTENANCE
---------------------------
Before an update:
1. Ask users to finish work and confirm all computers are connected.
2. Make and verify a database backup, then copy it to a separate secure place.
3. Confirm internet is available on the host and retain a copy of current
   application files if local changes have been made.

Run UPDATE_STATE_ISSUE.bat as administrator on the host. It downloads the
published repository files, stages them, runs the server tests, and only then
replaces changed application files. It does not replace the live database or
backups. If an update or service restart fails, it attempts to restore the
previous program files. Afterward reload the host and workstation browsers,
check the displayed version and test a normal workflow.

If the host has no internet connection, wait until it is available to use the
updater. Do not overwrite the database when copying program files. Never apply
an untrusted archive or unofficial code.

To uninstall the Windows service, use UNINSTALL_STATE_ISSUE_SERVICE.bat as
administrator. Uninstalling the service does not delete the program folder,
database, or backups. Keep the data until it has been separately backed up and
verified.

7. TROUBLESHOOTING
------------------
No connection on the host
- Open Services and check whether "State Issue Server" is Running.
- Try http://127.0.0.1:8787/ on the host.
- If the service is stopped, start it. If it fails, note the exact error and
  inspect Event Viewer > Windows Logs > Application.
- Verify the host is using the expected program and data folder. Do not delete
  or rename the database as a startup fix.

Host works, but workstations cannot connect
- Confirm the host and workstation are on the approved same network/VPN.
- Check the URL configured in OPEN_STATE_ISSUE.bat and confirm the host address
  has not changed.
- On the host, run SETUP_NEW_COMPUTER.bat as administrator to check its tests
  and firewall setup. Confirm TCP 8787 is allowed only on the intended private
  network/VPN.
- From the workstation, open the configured URL directly in a browser. If it
  works directly but the shortcut fails, correct the shortcut.
- If the host URL works locally but not remotely, ask the network administrator
  to check VPN routing/firewall policy. Do not open the port to the public
  internet or turn off Windows Firewall.

Internet unavailable
- Existing host and workstation use can continue over the local network.
- Online setup steps, first-time pywin32 installation, and GitHub updates will
  not work until internet access is restored. Do not remove Python or the
  service; record the pending maintenance and retry later.

Page looks old or does not update
- Reload the page; if necessary, use Ctrl+F5 to reload the application shell.
- Do not clear browser site data while the host shows pending offline changes.
- Check that the server and application files are from the same release.

"SERVER CONNECTION LOST" or changes not saving
- Stop entering changes on that workstation. Check service status and network.
- Reopen the configured host URL after connectivity is restored and confirm the
  current data loads before continuing.
- Do not restore a database merely because one client is disconnected.

"DATA NOT LOADED" or repeated save conflict
- Stop editing and preserve the database and backups. Record the exact message.
- Do not delete data, browser site data, or restore a backup without first
  verifying a backup and understanding which changes would be lost.

Service will not start
- Confirm Python is installed and available to the service, then inspect
  Windows Event Viewer > Windows Logs > Application.
- Confirm required program files exist and the service points to the intended
  installation folder. Rerun the service installer as administrator only after
  recording the error.
- Do not run a second server against the same database at the same time.

Backup verification fails
- Do not use that backup. Try an older backup and verify it.
- Preserve the failed file for diagnosis. Do not overwrite the live database
  until a verified restore file is available.

8. SUPPORT AND HANDOVER
-----------------------
Keep the repository URL, this guide, the host folder location, the configured
data folder, and the names of responsible administrators available to the
team. Do not put passwords or private network credentials in this guide.

When handing over, show at least two administrators how to:
- Check and restart the Windows service.
- Open the host and workstation URLs.
- Locate the database and backups.
- Verify a backup and perform a supervised restore.
- Run the automated tests and updater.
- Preserve and report an offline reconnect conflict.

When reporting a problem, include the app version, operating system, steps,
time of occurrence, and sanitized error text. Never attach operational records
to a public repository issue.
